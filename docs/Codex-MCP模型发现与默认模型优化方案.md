# Codex MCP 模型发现与默认模型优化方案

日期：2026-09-11  
状态：阶段一、阶段二已实施；用户级 Codex 配置迁移待执行。

## 1. 结论与目标

当前 Codex MCP 配置通过 `GROK_PROXY_DEFAULT_MODEL=grok-4.5` 固定了默认模型。项目具备模型发现能力，但此前默认优先读取本地缓存，缺少刷新时效管理；MCP 入口还把模型初始化与 API key 是否为空绑定。

建议分两阶段实施：先修复初始化、默认模型选择及启动发现，再按需加入长期运行进程的刷新能力。不要简单把所有 `grok-4.5` 替换成 `grok-4.6`，否则下次模型更新仍会重复出现问题。

本方案中“自动选择”指跟随 Grok CLI 明确给出的默认模型，不等同于按名称挑选版本号最大的模型。“最新清单”指通过已验证的上游刷新路径获取的清单；仅执行 `grok models` 尚不能证明它绕过 CLI 自身缓存。

## 2. 当前证据与边界

| 项目 | 已核实事实 | 影响 |
|---|---|---|
| Codex 配置 | `~/.codex/config.toml` 的 `mcp_servers.grok` 启动本项目 `.venv/bin/grok-proxy --mcp-stdio`，配置 ACP 后端和默认 `grok-4.5` | 未传 model 的工具调用默认使用 4.5 |
| 工具可见性 | 当前会话已发现 grok_consult、grok_review、grok_delegate 等工具 | 证明加载，不证明一次真实推理成功 |
| 当前缓存 | 本地解析得到 `grok-4.6`、`grok-4.5`，缓存默认取 4.6 | 可见列表已有 4.6，但配置覆盖默认值 |
| 配置覆盖 | 同一解析函数显式指定 4.5 时返回默认 4.5；不指定时返回 4.6 | 固定模型的直接原因已经复现 |
| 发现顺序 | 已改为自动模式下 CLI 优先、缓存降级；仍支持显式 `prefer_cli=False` | 正常启动会优先读取 CLI 清单 |
| MCP 初始化 | 已将模型解析抽成 `resolve_model_settings()`；有无 API key 均会调用 | 已设置 API key 时不再跳过模型发现 |
| HTTP 模型列表（旧行为） | `/v1/models` 只返回启动保存的 runtime_models | 这是本次长期运行刷新要补齐的缺口 |
| MCP model 参数 | 已统一复用 `resolve_request_model()`，显式真实 ID 可覆盖默认值 | MCP 与 HTTP 的别名行为一致 |

代码定位：

- `src/grok_proxy/__main__.py`：MCP 启动分支与路由初始化。
- `src/grok_proxy/bootstrap.py`：启动模型发现，以及回写 Settings 和进程环境变量。
- `src/grok_proxy/model_resolve.py`：缓存、CLI 解析、默认值覆盖和请求别名解析。
- `src/grok_proxy/mcp/server.py`：工具参数处理与默认模型使用。
- `src/grok_proxy/main.py`：HTTP 生命周期及 `/v1/models`。
- `src/grok_proxy/config.py`：环境变量与 `.env` 加载。

尚未核验：服务端当前完整模型清单、`grok models` 的联网与缓存刷新语义、真实推理端到端状态。本方案不将本地缓存当作服务端最新状态。

## 3. 范围与原则

- 保留 Codex → MCP stdio → Orchestrator → ACP → Grok CLI 调用链，不要求用户额外启动 HTTP 服务。
- 允许用户固定模型；固定模式是有效需求，不应被自动升级覆盖。
- 自动模式不按字符串或版本号排序选模型，不自动跨产品系列切换。
- MCP 和 HTTP 使用相同的模型选择规则；运行中请求继续使用创建时确定的模型。
- 保留无关客户端配置、工作区改动、认证数据和数据库内容。
- 不引入数据库迁移、独立模型注册中心或后台常驻调度器。
- 不因测试数据、README 示例含 4.5 就认定为缺陷；只修改影响实际行为或误导用户的内容。

## 4. 阶段一：必要修复

### 4.1 Codex 配置迁移

在代码修复后，建议将固定配置改为明确的自动模式：

```toml
[mcp_servers.grok.env]
GROK_BIN = "/Users/linmaogui/.grok/bin/grok"
GROK_PROXY_BACKEND = "acp"
GROK_PROXY_DEFAULT_MODEL = "auto"
```

使用显式 `auto` 比单纯删除变量更容易表达意图，也避免 `.env` 中的旧默认值重新生效。迁移前检查有效配置来源，仅读取模型相关字段，不输出其他环境变量或认证信息。

注意：当前 MCP 跳过 bootstrap 时，`auto` 可能被原样下传。因此应先完成初始化修复，再迁移配置。重启 MCP 进程后才会读取新配置；无需改变 Codex 主模型。

### 4.2 模型初始化独立于认证初始化（已实施）

将模型发现整理成供 MCP 和 HTTP 共用的轻量初始化函数，返回解析后的模型快照。无论 API key 是否存在，MCP 启动都执行该函数一次。

不要仅将整个 bootstrap 无条件执行：现有 bootstrap 包含认证文件和客户端配置写入，模型初始化不应因此产生无关副作用。

建议步骤：

1. 提取现有模型解析及 Settings 赋值逻辑，保留 bootstrap 对其调用。
2. MCP 有无 API key 两条路径均得到同样的模型快照，避免重复发现。
3. Router 接收模型快照，并复用 `resolve_request_model()` 解析请求。
4. 保持 API key 创建、客户端配置导出和数据库初始化的既有职责。

验收：有 key 与无 key、自动与固定配置四种组合均产生预期模型，不把 `auto` 下传给后端。

### 4.3 启动时优先查询 CLI（已实施）

正常启动采用 CLI 优先、缓存降级的发现顺序，复用现有 `prefer_cli` 能力。先验证本机 CLI 的 `models` 帮助和输出格式；若它支持明确的刷新选项，应核实后使用，禁止猜测参数或私有接口。

当前实现的失败处理规则：

| 场景 | 处理 |
|---|---|
| CLI 成功且得到有效清单 | 使用 CLI 清单及明确默认值 |
| CLI 成功但没有明确默认值 | 优先保留仍在清单中的已知默认值，否则按清单顺序取首个可用项，并注明来源 |
| CLI 超时、非零退出、格式无效 | 明确记录原因，读取有效缓存 |
| CLI 与缓存均失败，但用户明确指定真实模型 ID | 保留显式模型，标记清单未验证 |
| CLI 与缓存均失败且为自动模式 | 保留兼容性兜底 `grok-4.5`，同时写入 warning；后续可在严格部署模式改为启动失败 |

兼容性兜底仍是现有行为，但现在会显式记录 warning 和 `source=fallback`，不会伪装成 CLI/缓存发现。若生产环境要求“无清单不得启动”，可在阶段二增加严格模式；离线用户仍可使用有效缓存或固定模型。

CLI 解析应仅将退出码为零且结构有效的结果视为成功；stderr 用于诊断，不能将错误文本中的模型样式误解析为成功结果。沿用有限超时，不在启动时无限重试。

### 4.4 明确选择优先级与兼容性（已实施）

请求模型选择顺序：

1. 请求显式传入真实模型 ID：原样使用。
2. 请求未指定，或使用现有自动别名：使用有效默认值。
3. 有效默认值优先取用户固定配置，否则取发现结果默认值。

保留已有别名行为，包括 `grok-build` 系列兼容映射。保持未知真实 ID 的透传行为，由 CLI 返回具体错误，避免过期清单阻止使用刚发布的模型。

`GROK_PROXY_MODELS` 继续表达显式公布列表，不在本次修改中悄悄改为访问控制白名单。若固定默认值不在列表中，给出清晰诊断；是否调整公布列表须保持 MCP/HTTP 一致并用测试固定。

`grok_resume` 保持沿用原请求模型，不因刷新后默认模型变化而自动切换。

### 4.5 可观测性（已实施）

日志现在包含：有效默认模型、清单和默认值来源；fallback、CLI 非零退出、空输出和缺少默认值会记录 warning。模型快照接口返回最近尝试、最近成功时间、过期状态和最后错误。MCP 日志只能输出到 stderr，stdout 保持 JSON-RPC 协议纯净。

区分两个概念：清单查询时间与上游数据更新时间。读取本地缓存的时间不是缓存内容生成时间，CLI 查询成功也不自动等于联网刷新成功。

## 5. 阶段二：长期运行的刷新能力（已实施）

运行时模型注册表已接入 MCP、HTTP 和响应创建路径。长时间运行的进程会按 TTL 检查清单，也可通过接口立即刷新。

### 5.1 最小接口

MCP 工具 `grok_models` 支持只读查看快照，及显式 `refresh=true` 重新发现。返回清单、有效默认值、来源、最近查询时间、过期状态及最后错误。刷新仅更新本进程模型快照，不重写 Codex 或其他客户端配置。

HTTP `/v1/models` 保留原有 JSON 响应结构；`?refresh=true` 强制刷新，并通过 `X-Grok-Model-*` 响应头返回来源、默认值、过期状态和最近成功时间。健康接口增加模型来源和过期标记。MCP 与 HTTP 若是不同进程，各自刷新各自快照，不承诺跨进程即时同步。

### 5.2 按需过期刷新

新响应创建、MCP 模型工具和 HTTP 模型查询都会检查快照查询年龄；默认刷新间隔 30 分钟，可通过 `GROK_PROXY_MODEL_REFRESH_INTERVAL_SEC` 调整，不宣称是上游有效期。

- 同一进程内并发请求共享一次刷新，避免多个 `grok models` 同时启动。
- 使用异步子进程或线程卸载现有同步调用，不能阻塞 MCP ping 和状态查询。
- 成功解析完整新快照后再原子替换；失败保留最后一次成功快照。
- 失败后设置下一次允许尝试时间，防止每个请求重复超时。
- 用户固定默认模型不随清单刷新改变。
- 创建响应时锁定模型 ID；刷新不改变已排队、运行或恢复的响应模型。

刷新依据进程启动时捕获的原始用户配置重新计算。现有 bootstrap 会把发现结果写入进程 Settings 和环境变量，但注册表不使用这些派生值作为固定配置，因此自动模式不会被第一次发现结果锁定。CLI 启动 HTTP 服务时直接把 bootstrap 创建的注册表传给应用实例，避免重新导入已物化的环境变量后丢失这一 provenance。

## 6. 实施任务与验收

所有代码任务开始前先检查工作区差异，仅修改本方案涉及文件。下表的测试均先构造旧实现失败的案例，再实施最小修复。

| 顺序 | 任务 | 主要文件 | 可观察验收 |
|---|---|---|---|
| 1 | 验证 CLI 清单/刷新语义 | CLI 帮助与命令输出证据 | 明确能否联网刷新、默认字段和退出码语义 |
| 2 | 修复 key 导致跳过初始化 | `__main__.py`、`bootstrap.py` | 有/无 key 的模型选择一致，发现仅执行一次 |
| 3 | 启动 CLI 优先及失败处理 | `model_resolve.py` | 旧缓存不遮蔽成功 CLI；失败降级可诊断 |
| 4 | MCP 统一别名解析 | `mcp/server.py` | auto/省略/固定/显式覆盖结果正确 |
| 5 | 更新集成文档与配置示例 | 两份 README、`docs/clients/codex-mcp.md` | 区分自动与固定模式，说明重启及离线行为 |
| 6 | 模型查看与刷新 | 模型运行时、MCP、HTTP 接入点 | 清单与默认值一致更新，不阻塞 ping，不更改旧请求 |
| 7 | 配置迁移和实机验收 | 用户 Codex MCP 配置 | 重启后自动选择有来源依据，真实调用到达终态 |

### 回归案例

1. 缓存仅含旧模型，而 CLI 返回新模型与明确默认值：采用 CLI。
2. CLI 非零退出但输出包含 `- grok-...`：不得视为成功。
3. CLI 超时且缓存有效：使用缓存并记录降级。
4. 两者失败、自动模式：明确失败；固定模型：允许透传并说明未验证。
5. 配置固定 4.5、发现默认 4.6：省略 model 仍使用 4.5。
6. 自动模式、发现默认 4.6：省略 model 和显式 auto 都使用 4.6。
7. 单次显式真实模型覆盖默认值；未知 ID 保留透传兼容性。
8. 缓存 hidden 模型过滤继续生效；空清单、畸形 JSON 和 CLI 格式变化不会产生伪成功。
9. MCP 已设置 API key 时仍执行模型解析，不原样下传自动别名。
10. 刷新从 A 默认切到 B 默认：新请求用 B，已有请求及 resume 沿用 A。
11. 并发过期请求只触发一次刷新；刷新失败不清空快照，ping 仍及时响应。
12. 第二次刷新仍遵循原始自动配置，不将第一次发现结果误判为固定配置。

## 7. 发布与回退

1. 先完成代码与回归测试，再审阅最终差异，确认没有无关改动。
2. 用户配置迁移前保留受限访问的本地恢复副本，不提交完整 Codex 配置或认证数据。
3. 仅修改 Grok MCP 的默认模型项，重启对应 MCP 进程并检查生效来源。
4. 若自动模式异常，恢复原有固定模型配置并重启；无需删除缓存、重建数据库或变更 Codex 主模型。
5. 阶段二作为独立提交，便于单独回退刷新能力，保留阶段一初始化修复。
