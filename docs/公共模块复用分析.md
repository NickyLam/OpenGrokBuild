# OpenGrokBuild（Grok-Build-Cli-Proxy）公共模块复用分析

> **分析对象**：`OpenGrokBuild`（`src/grok_proxy/`，约 9k 行 Python）  
> **分析日期**：2026-08-03  
> **目的**：在多人协作背景下，识别「各模块各自实现、可统一抽象」的能力，降低技术债与行为分叉风险。  
> **原则**：优先抽**已出现 ≥2 次的横切能力**；领域核心（Orchestrator 状态机、Backend Protocol）保持单一真相源，不做过度抽象。

---

## 1. 现状总览

### 1.1 模块地图

| 包 / 模块 | 职责 | 体量（约） | 复用成熟度 |
|-----------|------|------------|------------|
| `runtime/orchestrator.py` | Response 生命周期、事件订阅、权限等待 | 807 行 | 核心业务，已是聚合根 |
| `storage/database.py` | SQLite 读写 + 部分仓储逻辑 | 647 行 | 偏「上帝对象」，需拆仓储 |

| `credentials.py` | 主密钥、客户端配置安装 | 682 行 | 安装逻辑三份拷贝 |
| `backends/acp.py` / `headless.py` | 两种 Grok 运行时 | 518 / 320 行 | Protocol 已统一，映射/进程未统一 |
| `api/responses.py` | Responses API + SSE | 211 行 | 与 Chat SSE 重复 |
| `openai_sse.py` | Chat OpenAI SSE 适配 | 318 行 | 仅 Chat 用，与 journal SSE 分裂 |

### 1.2 已做得较好的抽象（应保留并强化）

这些能力**已经**是公共层，后续新功能应复用，而不是旁路：

| 能力 | 位置 | 说明 |
|------|------|------|
| Backend 协议 | `backends/base.py` | `GrokBackend` / `BackendEvent` / `BackendSessionRequest` |
| 内部命令对象 | `runtime/commands.py` | `CreateResponseCommand` + `GrokExtensions` |
| 状态机 | `runtime/state_machine.py` | 合法迁移集中定义 |
| 错误模型 | `errors.py` | `ProxyError` + OpenAI 形错误体 |
| 并发闸门 | `concurrency.py` | 全局 + per-key |
| Scope | `scopes.py` | 权限字符串枚举 |
| 进程终止 | `process_manager.terminate_process_tree` | Runner / ProcessManager 共用 |

## 2. 重复与分叉清单（按优先级）

### P0 — 高价值 / 高分叉风险（建议优先统一）

#### 2.1 请求入口适配层：Chat / Responses / MCP 三套「拼装 Command」

**现象**

| 入口 | 位置 | 各自实现的逻辑 |
|------|------|----------------|
| Chat Completions | `main.py` `_chat_to_command` / `_chat_command_with_auth` | cwd、rules、always_approve、auth 元数据、timeout 裁剪 |
| Responses API | `api/responses.py` `create_response` | x_grok 合并、scoped key 策略、workspace_mode、timeout 裁剪 |
| MCP Tools | `mcp/server.py` `_create` 等 | 手写 `CreateResponseCommand` + 默认 workspace/permission |

**风险**

- 新加 `x_grok` 字段时只改一条路径 → 客户端行为不一致。
- Scoped key 的 `workspace_mode` / `permission_policy` 约束只在 Responses 路径完整，Chat 路径可能更松。
- MCP 默认策略（consult=read_only、delegate=worktree）散落在 tool handler，难做统一审计。

**建议公共组件**

```
grok_proxy/application/
  create_response_builder.py   # 统一：AuthContext + Settings + raw request → CreateResponseCommand
  request_guards.py            # require_scopes + check_workspace + session_cwd + timeout clamp
```

**统一接口示意**

```python
def build_create_command(
    *,
    model: str,
    input_text: str,
    stream: bool,
    background: bool,
    x_grok: dict | GrokExtensions,
    auth: AuthContext,
    settings: Settings,
    previous_response_id: str | None = None,
    metadata: dict | None = None,
) -> CreateResponseCommand: ...
```

Chat / Responses / MCP **只负责解析本协议**，最终都走该 builder。

---

#### 2.2 SSE 传输层：三处手写 StreamingResponse + 两套帧格式

**现象**

1. `main.py` Chat stream：`stream_openai_sse_from_journal` + 固定 headers  
2. `api/responses.py` create stream：手写 `id/event/data` 帧 + 同样 headers  
3. `api/responses.py` GET events：与 #2 **几乎相同的** event 序列化循环  
4. `openai_sse.py` 另有从 raw Grok events 转换的遗留路径（与 journal 路径并存）

**重复片段（headers 三处拷贝）**

```python
headers={
    "Cache-Control": "no-cache",
    "Connection": "keep-alive",
    "X-Accel-Buffering": "no",
}
```

**建议公共组件**

```
grok_proxy/http/sse.py
  SSE_HEADERS
  format_sse_event(id, event, data) -> str
  stream_journal_sse(orch, response_id, after) -> AsyncIterator[str]
  stream_openai_chat_sse(...)  # 现有 openai_sse 收敛到此
  sse_streaming_response(iterator) -> StreamingResponse
```

**收益**

- Metrics（`sse_connections_*`）只在一处增减，避免漏记。
- Last-Event-ID / `after` 续传逻辑不复制。
- 后续加压缩、心跳、鉴权断流策略只改一处。

---

#### 2.3 Backend 事件映射：Headless vs ACP 两套平行 mapper

**现象**

| 源格式 | 映射函数 | 文件 |
|--------|----------|------|
| Grok `streaming-json` | `map_streaming_event` | `backends/headless.py` |
| ACP `session/update` | `map_session_update` | `backends/acp_map.py` |

两者目标都是 `BackendEvent`（text / tool_call / tool_update / tool_result / plan / permission / usage / end / error），字段归一逻辑高度同构（id 多别名、arguments 多键名等）。

**Usage 归一也分裂**

- `grok_runner.map_usage` → `(prompt_tokens, completion_tokens, total_tokens)`  
- `acp_map.normalize_usage` → camelCase → snake_case dict  

**建议公共组件**

```
grok_proxy/backends/event_normalize.py
  normalize_tool_id(raw) / normalize_tool_name(raw)
  normalize_usage(raw) -> UsageModel   # 统一模型
  BackendEventBuilder                  # 构造 text/tool/permission/end

grok_proxy/backends/mappers/
  headless_map.py   # 薄：协议字段 → Builder
  acp_map.py        # 薄：协议字段 → Builder（现有 acp_map 迁入）
```

**协作约定**：新增事件类型时，只扩展 `BackendEventType` + Builder；各 mapper 补解析，禁止在 Orchestrator 再写 if-else。

---

#### 2.4 密钥与敏感文件：两套 Key 规范 + 多处 0600

**现象**

| 用途 | 生成函数 | 前缀 | 位置 |
|------|----------|------|------|
| 主代理密钥（文件） | `credentials.generate_api_key` | `sk-gp-` | `credentials.py` |
| 作用域 API Key | `api_keys.generate_api_key` | `gp_live_` / `gp_test_` | `api_keys.py` |
| 私有文件权限 | `_chmod_private` / `os.chmod(..., 0o600)` | — | credentials 多处 + headless prompt 文件 |

**风险**

- 新人易混「主密钥」与「scoped key」的生命周期与存储（明文文件 vs hash+pepper）。
- 临时 prompt 文件、client 配置、api_key 文件的安全写路径不一致（备份、atomic write 有无不定）。

**建议公共组件**

```
grok_proxy/security/
  secrets.py          # generate_master_key / generate_scoped_key / mask_secret
  secure_fs.py        # write_private_file(path, data)、atomic_json_write、ensure_private_dir(0o700)
  redact.py           # 从 headless._redact_secrets 提升为全局日志脱敏
```

### P1 — 中等价值（减少样板与配置分叉）

#### 2.5 客户端配置安装：WorkBuddy / OpenCode / Pi Agent 三份 Upsert

**现象**（均在 `credentials.py`）

- `install_workbuddy_model`  
- `install_opencode_model`  
- `install_pi_agent_model`  

共性骨架：

1. 解析路径 / 确保父目录  
2. `_load_json_file`  
3. 按 id/url 查找并 merge  
4. `_backup_json`  
5. `write_text` + `_chmod_private`  

差异仅在：JSON 形状（list vs nested providers）、匹配键、entry 构造（`workbuddy_model_entry` / `generic_client_config` 片段）。

**建议公共组件**

```
grok_proxy/clients/
  base.py             # JsonConfigUpserter：load → mutate → backup → write_private
  workbuddy.py
  opencode.py
  pi_agent.py
  model_entry.py      # workbuddy_model_entry / generic_client_config（已存在，迁入）
```

新增客户端（Cursor / Continue / Aider 等）只加 adapter，不复制 IO 骨架。

---

#### 2.6 模型能力与 Usage：缓存探测 + 双套 usage

**现象**

- `model_resolve.py`：缓存 / CLI 探测、`ModelCapabilities`、`resolve_request_model`（**已较集中**）  
- Chat 输出用 `map_usage`；ACP 用 `normalize_usage`；SSE 再各自拼 usage 字段  

**建议**

- 将 `map_usage` 与 `normalize_usage` 合并为 `protocol/usage.py` 的单一 `Usage` 值对象 + `to_openai()` / `to_internal()`。  
- `ModelCapabilities` 保持在 `model_resolve`，但禁止 API 层硬编码 `supports_*` 默认值（一律走 `get_model_capabilities`）。

---

#### 2.7 HTTP API 横切：鉴权 / metrics / orch 取用

**现象**

各 router 重复：

```python
auth = get_auth_context(request)
auth.require_scopes(...)
orch = request.app.state.orchestrator
m = getattr(request.app.state, "metrics", None)
```

`api/permissions.py`、`api/keys.py`、`api/responses.py`、`main.py` 各自写一遍。

**建议公共组件**

```
grok_proxy/api/deps.py
  get_orchestrator
  get_metrics
  get_settings
  require_scope(*scopes)   # FastAPI Dependency
  require_auth             # 已有雏形，统一导出
```

---

#### 2.8 进程生命周期：Runner / ACP / ProcessManager 仍有重复

**已统一**：`terminate_process_tree`。

**仍分散**：

| 能力 | Headless/GrokRunner | ACP | ProcessManager |
|------|---------------------|-----|----------------|
| `create_subprocess_exec` + pipe | ✓ | ✓ | — |
| `start_new_session` / killpg | ✓ | 部分 | reclaim |
| 注册/注销 pid 文件 | 经 PM | 应经 PM | ✓ |
| stdout 按行 JSON 解析 | ✓ | ✓ NDJSON RPC | — |

**建议公共组件**

```
grok_proxy/runtime/subprocess_util.py
  spawn_tracked(cmd, *, cwd, env, process_manager, response_id) -> Process
  read_json_lines(stream) -> AsyncIterator[dict]   # NDJSON 共用
```

ACP 的 JSON-RPC 帧可建立在 `read_json_lines` 之上。

---

#### 2.9 Workspace / Git 子进程：manager 内联 subprocess

`workspace/manager.py` 内多处 `subprocess.run`（git worktree、diff、is_repo）。

**建议**

```
grok_proxy/workspace/git_ops.py   # is_git_repo / create_worktree / remove_worktree / diff
```

便于单测 mock，也避免与未来「临时目录拷贝 / sandbox」混在同一类。

### P2 — 结构债（中长期，防继续膨胀）

#### 2.10 `storage/database.py` 上帝对象

单文件同时承担：连接管理、迁移调用、responses/events/sessions/permissions/api_keys/audit/locks 的 SQL。

**建议拆分**

```
storage/
  database.py          # 连接、事务、meta
  migrations.py        # 已有
  repositories/
    responses.py
    events.py
    sessions.py
    permissions.py
    api_keys.py
    workspace_locks.py
    audit.py
```

**协作约定**：业务代码只依赖 Repository 接口，禁止新 SQL 散落在 Orchestrator 外（目前 Orchestrator 已依赖 db 方法，迁移时保持方法签名兼容）。

---

#### 2.11 `main.py` 装配与 Chat 路由耦合

`create_app` 同时：bootstrap、DI、health/ready、models、connection、**完整 Chat Completions 实现**。

**建议**

```
api/chat.py            # 从 main 迁出 Chat 路由
app_factory.py         # create_app 只装配
```

与 `api/responses.py` / `api/permissions.py` / `api/keys.py` 对称。

---

#### 2.12 Orchestrator 过重（807 行）

合理聚合根，但可内部切分（同包私有模块，不必过度接口化）：

```
runtime/orchestrator/
  __init__.py          # 门面
  create.py            # create/start
  run_loop.py          # backend event 消费
  permissions_wait.py
  streaming.py         # subscriber fan-out
```

目标：多人改「权限等待」与「事件落库」时减少冲突。

---

#### 2.13 错误类型层次不完整

现有：`ProxyError`、`BackendError`、HTTP handler。

**缺口**

- BackendError → ProxyError 的映射分散在 Orchestrator。  
- 校验错误 / 鉴权错误 / 后端错误 的 `code` 字符串未集中枚举。  

**建议**

```
errors.py 扩展
  ErrorCode(StrEnum)
  from_backend_error(exc: BackendError) -> ProxyError
```

---

#### 2.14 与 Grok-GUI 的跨仓契约（可选、协议层）

同生态的 `Grok-GUI` 自建 Tauri + ACP 客户端（permissions / worktrees / sessions），与 Proxy 的 HTTP/ACP 语义重叠但**代码不共享**。

**不建议**强行 monorepo 共享运行时；建议共享的是：

| 契约 | 形式 |
|------|------|
| `x_grok` 扩展字段 | JSON Schema / OpenAPI 片段（Proxy `docs/API-CONTRACT-SNAPSHOT.md` 生成） |
| Permission 决策枚举 | 文档 + 单测快照，GUI 对齐 |
| BackendEvent 语义 | 内部文档，避免两边「tool_call id」字段名漂移 |

## 3. 推荐目标包结构（增量演进，非大爆炸重写）

```text
src/grok_proxy/
  application/           # 【新增】用例层：build command、guards
  http/                  # 【新增】SSE、公共 StreamingResponse
  security/              # 【新增】secrets、secure_fs、redact
  clients/               # 【从 credentials 拆】各 Agent 客户端安装器
  api/
    deps.py              # 【新增】FastAPI 依赖
    chat.py              # 【从 main 迁】
    responses.py
    permissions.py
    keys.py
  backends/
    event_normalize.py   # 【新增】
    mappers/             # headless_map / acp_map
  protocol/
    usage.py             # 【新增】统一 usage
    responses_models.py
  storage/repositories/  # 【渐进拆】
  runtime/               # orchestrator 可内拆子模块
  ...
```

**迁移策略（多人协作友好）**

1. **先加新模块，旧路径 re-export**（不一次性改 import 全仓）。  
2. 每个公共模块配 **单元测试** 锁行为，再让 Chat/Responses/MCP 切过去。  
3. 一次 PR 只收敛一类横切（例如只做 SSE），避免「大重构 PR」。  
4. 在 `docs/ARCHITECTURE.md` 增加「公共模块所有权」表：谁维护、谁可以改契约。

## 5. 协作规范（防技术债回流）

### 5.1 「何时必须用公共模块」检查清单

新增功能前自检：

- [ ] 是否新增 HTTP 流式响应？→ 用 `http/sse`，禁止手写 headers。  
- [ ] 是否创建 Grok 任务？→ 用 `application.build_create_command`，禁止直接 `CreateResponseCommand(...)` 散落默认值。  
- [ ] 是否解析 Grok/ACP 事件？→ 用 `event_normalize` + 对应 mapper。  
- [ ] 是否写含密钥的文件？→ 用 `security.secure_fs`。  
- [ ] 是否安装客户端配置？→ 用 `clients.JsonConfigUpserter`。  
- [ ] 是否新 SQL？→ 只进 `storage/repositories/*`。  

### 5.2 禁止事项

| 禁止 | 原因 |
|------|------|
| 在 router 内拼 `always_approve` / timeout 业务规则 | 与 scoped key 策略分叉 |
| 复制 `map_streaming_event` 改一版 ACP | 事件语义漂移 |
| 新造第三种 API Key 前缀 | 运维与文档混乱 |
| Orchestrator 内直接 `subprocess` | 绕过 ProcessManager 回收 |
| 在业务模块 `print` 密钥 / 未 redact 的 stderr | 安全事故 |

### 5.3 建议的 Code Review 焦点

1. **默认值来源**：是否全部来自 Settings / AuthContext，而非魔法数。  
2. **错误 code**：是否落在 `ErrorCode` 枚举。  
3. **测试**：公共模块必须有 unit；入口切换需 integration 锁「三路径同 command 字段」。

## 7. 结论

当前代码库在 **Backend Protocol、Orchestrator、State Machine、Permissions** 上已经具备正确的「深模块」边界；主要技术债不在领域核心，而在：

1. **多协议入口**（Chat / Responses / MCP）对同一用例的重复装配；  
2. **传输层**（SSE）与 **事件归一**（Headless / ACP）的平行实现；  
3. **安全 IO 与客户端安装** 的复制粘贴扩张；  
4. **存储与 App 装配** 文件过大导致的协作冲突。

优先抽取 **application builder、SSE、event_normalize、security** 四类公共模块，即可在不大规模重写业务的前提下，显著降低多人协作下的行为分叉与重复劳动。后续再渐进拆分 `clients/`、`storage/repositories` 与 `main` 路由，控制包体量即可。
